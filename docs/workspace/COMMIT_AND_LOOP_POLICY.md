# Commit And Loop Policy

This workspace uses strict commit buckets and quality gates so that product history stays reviewable.

## Commit Split

Use only one commit type per bucket.

- `feat:` product code that changes real game behavior
- `docs:` durable documentation worth keeping
- `chore:` environment, build cleanup, ignore rules, generated output cleanup, and tracking cleanup

Do not place the following in a `feat:` commit:

- `progress-*`
- `BATCH_*`
- `SPRINT_*`
- repeated run reports
- generated outputs
- build artifacts

## Tracking Exclusion

Keep these out of Git unless there is a strong product reason:

- repeated run logs and reports
- temporary outputs
- caches and local build products
- placeholder or autogenerated files that are not shipped with the product

If a file is useful for local recovery, move it to local backup storage instead of keeping it in product commits.

## Harness Loop Quality Rule

Each loop must include at least one meaningful functional change.

The following do not count as a completed loop:

- no-op changes
- text-only toggle changes
- pure number bumps with no rule change

Each loop should leave a small record with:

- changed files
- a real diff summary
- validation results

## Balance Change Rule

Balance changes must not be number inflation only.

Do not treat these as valid balance work:

- repeating stage5 reward increases
- changing reward numbers without a rule change

Valid balance work should include all of the following:

- a gameplay rule change
- a short rationale
- a validation result

Examples:

- time-limit bonus rule change
- boss wave entry rule change
- reward formula structure change

## Pre-Commit Checklist

Before staging, confirm:

1. Is this real product behavior?
2. Is this durable documentation?
3. Is this environment or cleanup work?
4. Is this just a generated log, report, or artifact?

If the answer is `4`, remove it from the commit first.
