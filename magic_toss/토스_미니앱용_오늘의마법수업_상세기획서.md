# 토스 미니앱용 게임 기획서

## 오늘의 마법수업: 결계시험

기존에 기획한 ‘마법 수업을 코어 펀으로 삼는 모바일 게임’을 토스 미니앱 환경에 맞게 다시 설계한 상세 기획서다. 핵심 목표는 ‘스펙이 너무 커지지 않도록’ 통제하면서도, 토스 문서에서 요구하는 광고·QA·검수·정산 흐름을 자연스럽게 만족하는 출시 가능한 설계를 만드는 것이다.

## 요약

- **장르**: 세로형 오토배틀 로그라이크 디펜스 + 마법학교 라이프 메타
- **한 줄 피치**: 수업으로 주문을 배우고, 실기시험에서 자동 전투로 검증하는 2~3분 세션형 학교 RPG
- **플랫폼 적합성**: 토스 미니앱 게임 카테고리, 전체 화면, 짧은 세션, 광고 친화적 결과 화면
- **개발 방식**: WebView 중심 경량 구현, Vite(React+TypeScript) 계열 문법 기준, 서버 없는 MVP 지향
- **로그인/식별**: 게임 로그인(getUserKeyForGame) 사용, 별도 서버·동의 절차 없는 진입
- **출시 범위**: 1인 학생 캐릭터, 4개 학파, 30개 스테이지, 리워드/전면 광고만 우선 적용
- **수익화**: 광고 우선 MVP. 인앱 결제·배너 광고·랭킹·길드·PVP는 출시 후 검토

## 1. 왜 토스 미니앱에 맞는가

앱인토스는 파트너 서비스가 토스 앱 안에서 앱인앱 형태로 노출되는 플랫폼이며, WebView와 React Native 기반 SDK를 제공한다. 게임은 일반적으로 2~4주 정도면 출시 가능하다고 안내되고 있고, 현재 이용자는 만 19세 이상을 기준으로 한다 [T1]. 이 조건은 ‘가볍고 빠르게 시작할 수 있는 게임’에 유리하다.

또한 앱인토스는 전체 탭과 검색을 통해 게임 미니앱을 노출할 수 있고, 광고·정산·검수 흐름까지 콘솔 안에서 운영할 수 있다 [T1]. 따라서 초기에 대규모 라이브 서비스보다, 짧은 세션과 명확한 광고 포인트를 가진 미니게임형 구조가 훨씬 적합하다.

> **결론** 토스판에서는 기존 ‘마법학교 RPG’를 그대로 이식하지 않는다. 대신 ‘마법 수업 선택 → 2~3분 실기시험 → 결과 보상’ 구조로 축소해, 토스의 짧은 진입과 빠른 반복 문법에 맞춘다.

## 2. 토스 문서 기반 제품 제약과 해석

공식 문서상 게임 미니앱은 SDK/API를 통해 빠르게 개발할 수 있지만, 2026년 3월 23일 이후에는 SDK 1.x로 빌드한 번들을 업로드할 수 없고, 최신 SDK 2.x 계열 전제를 잡아야 한다 [T2]. 또한 앱 출시는 운영·기능·디자인·보안 4단계 검수를 거치며, 게임은 반드시 심의를 완료해야 한다 [T2].

게임 출시 가이드에는 최초 화면 10초 이내 진입, 전체 화면 구현, 안전 영역 준수, 닫기 버튼 동작, 종료 경로 제공, 진입 직후 바텀시트 금지, 예측 가능한 CTA, 백그라운드 전환 시 사운드 정지, 복귀 시 사운드 재개, 플레이 데이터 유지 등이 포함돼 있다 [T3].

광고 문서에서는 전면형·보상형·배너 광고를 지원하지만, 게임형 서비스의 배너는 상단/하단 빈 영역에만 둘 수 있고 화면 중앙에는 둘 수 없다. 광고는 예상하기 어려운 순간에 등장하면 안 되고, 인트로/로딩/컷신/팝업 같은 일시적 화면에는 지양해야 한다 [T4][T5].

보상형 광고는 사용자가 자발적으로 선택할 때 쓰는 것이 맞고, QA 문서에서는 보상 지급이 시청 완료 이벤트에서만 발생해야 하며, 중복 보상 방지와 빈도 제한·쿨다운을 확인하라고 요구한다 [T5][T6].

> **제품 원칙** 토스 제약을 반영한 결과, MVP는 ① 첫 화면 즉시 진입, ② 전투 중 조작 최소화, ③ 광고는 결과/부활 등 예측 가능한 순간에만 노출, ④ 배너는 런칭에서 제외, ⑤ 로그인/서버 의존도를 최대한 줄이는 설계가 가장 안전하다.

## 3. 스코프 통제 원칙

이번 기획은 ‘바이브 코딩으로 만들 수 있는 수준’이 핵심이다. 따라서 처음부터 세계관, 라이브 운영, 멀티플레이, 뽑기, 시즌 패스, 길드, 랭킹, 장비 수집, 실시간 PVP를 넣지 않는다. 기능이 많아질수록 토스 검수, 광고 QA, 세이브, 사운드, 복귀 처리까지 모두 복잡해진다.

| 포함 | 제외 |
|---|---|
| 학생 1명 중심 성장 | 여러 영웅 수집 시스템 |
| 4개 학파와 16개 주문 | 수십 개 학파/대규모 스킬트리 |
| 30개 스테이지 + 일일 도전 1종 | 오픈월드/대형 캠페인 |
| 오토배틀 + 선택 카드 | 실시간 수동 컨트롤 액션 |
| 광고 중심 수익화 | 출시 동시 인앱 결제/가챠 |
| 로컬 저장 중심 MVP | 서버 필수 랭킹/길드/실시간 동기화 |
| 세로형 1화면 플레이 | 다층 메뉴와 복잡한 하위 시스템 |

> **개발 판단** ‘코어가 선명한 작은 게임’으로 출시하고, 검증 이후에만 클라우드 세이브·랭킹·IAP·배너 광고를 단계적으로 붙인다.

## 4. 게임 컨셉

게임명 가칭은 ‘오늘의 마법수업: 결계시험’이다. 플레이어는 마법학교 학생으로서 매번 수업을 하나 선택해 그날의 주문 세트를 준비하고, 이후 시작되는 실기시험에서 학교의 결계석을 지켜야 한다. 전투는 자동으로 진행되며, 플레이어는 전투 중간중간 교수의 피드백 카드 3개 중 하나를 골라 빌드를 강화한다.

이 구조는 기존 마법학교 시리즈의 ‘원하는 마법을 배운다’는 감성을 살리면서도, 토스 미니앱에 맞는 짧은 세션과 광고형 결과 화면을 만들기 쉽다. 전투를 오토배틀로 두면 조작 학습 비용이 낮아지고, 첫 접속자의 즉시 플레이 전환이 쉬워진다.

> **핵심 감정** 내가 듣고 싶은 수업을 고르고, 그 결과가 오늘의 실기시험에서 바로 통하는지 확인하는 재미.

## 5. 코어 펀

- **수업 선택의 즐거움: **전투 전에 ‘오늘은 화염 실습을 들을까, 보호술 이론을 들을까’를 고르게 한다.
- **즉시 체감되는 성장: **수업 직후 같은 세션 안에서 실기시험을 치르게 해 배운 주문의 효용을 바로 확인하게 한다.
- **오토배틀 설계의 재미: **직접 싸우는 대신, 어떤 주문을 장착했고 어떤 강화 카드를 골랐는지가 승패를 가르게 한다.
- **학생 정체성의 축적: **같은 화염 계열이라도 폭딜형, 지속화상형, 방어 겸용형처럼 자기 스타일이 축적된다.

정리하면 이 게임의 코어 펀은 ‘전투 자체의 손맛’보다 ‘오늘의 수업 선택이 빌드가 되고, 빌드가 결과로 돌아오는 감각’에 있다. 이 방향은 토스 광고 정책의 ‘예측 가능한 순간’과도 잘 맞는다. 사용자가 기대한 흐름을 방해하지 않고, 수업-시험-결과라는 자연스러운 전환점 사이에만 광고를 넣을 수 있기 때문이다 [T4][T5].

## 6. 코어 루프와 세션 루프

| 단계 | 시간 | 플레이어 행동 | 시스템 결과 | 광고 가능 여부 |
|---|---|---|---|---|
| 로비 진입 | 10~20초 | 오늘의 수업 제안 확인 | 오늘의 3과목 제시 | 아니오 |
| 수업 선택 | 20~30초 | 1과목 선택 | 시작 주문/패시브/보너스 부여 | 아니오 |
| 실기시험 | 90~150초 | 웨이브 중 카드 3지선다 선택 | 오토배틀 진행 | 아니오 |
| 결과 화면 | 10~20초 | 보상 수령/재도전/다음 스테이지 | 성장 재화 지급 | 예, 전면 광고 후보 |
| 선택 보상 | 5~15초 | 이어하기/x2보상/수업 리롤 선택 | 광고 시청 시 추가 보상 | 예, 보상형 광고 |
| 강화/정비 | 20~40초 | 도서관 업그레이드 | 영구 성장 반영 | 아니오 |

한 세션은 2분 반에서 4분 정도를 목표로 한다. 토스 안에서 잠깐 열어도 끝까지 플레이가 가능해야 하므로, 매번 긴 스토리나 탐험을 붙이지 않는다. 오히려 ‘짧게 열고 한 판 끝내기’를 중심으로 하고, 누적 플레이는 도서관 업그레이드와 학파 숙련도로 쌓는다.

## 7. 플레이 구조 상세

### 7-1. 수업 선택 시스템

매일 또는 세션마다 3개의 수업 카드가 뜬다. 카드에는 과목명, 시작 주문, 추가 패시브, 오늘의 보너스가 표시된다. 플레이어는 그중 하나를 골라 오늘의 시작 빌드를 결정한다. 수업 카드는 전투 입장 전 단 한 번의 선택으로 끝나야 하며, 지나치게 복잡한 시간표 관리나 일정을 넣지 않는다.

| 학파 | 역할 | 대표 주문 | 초보 체감 |
|---|---|---|---|
| 화염학 | 광역 딜 / 화상 누적 | 화염탄, 불기둥, 잿불 고리, 유성 파편 | 화끈하고 이해가 쉬움 |
| 냉기학 | 둔화 / 정지 / 안전한 운영 | 얼음 파편, 서리 안개, 빙결파, 빙창 | 실패가 적고 안정적 |
| 보호술 | 결계 유지 / 생존 / 반사 | 보호막, 다중 방패, 반사막, 응급 수복 | 진행 막힘 해소에 유리 |
| 연금학 | 지속 효과 / 보조 / 자원 관리 | 산성 플라스크, 자동 회복약, 마력 추출, 변환 포션 | 중후반 운영 폭 넓음 |

### 7-2. 전투 시스템

전투는 세로형 전체 화면에서 진행되며, 플레이어 학생은 화면 하단 결계석 근처에 위치한다. 적은 상단에서 내려오고, 학생은 장착한 주문 우선순위에 따라 자동으로 시전한다. 실질적 조작은 ‘레벨업 시 3개 카드 중 1개 선택’뿐이다.

- **런 기본 규격: **1판 8웨이브, 90~150초, 보스 웨이브 1회.
- **장착 규격: **액티브 주문 4개, 패시브 2개, 유물 1개.
- **전투 내 선택: **경험치 임계치 도달 때마다 카드 3개 중 1개 선택.
- **실패 조건: **결계석 체력 0 또는 제한 시간 내 보스 정리 실패.
- **성공 조건: **보스 처치 또는 웨이브 완료.

### 7-3. 성장 구조

메타 성장은 두 층으로만 제한한다. 첫째는 학파 숙련도, 둘째는 도서관 영구 업그레이드다. 학파 숙련도는 특정 학파 수업을 자주 들을수록 올라, 시작 카드와 고급 주문 후보를 늘려 준다. 도서관 업그레이드는 모든 플레이에 적용되는 영구 강화다.

| 성장 축 | 재화 | 효과 예시 | MVP 범위 |
|---|---|---|---|
| 학파 숙련도 | 수업 기록 | 해당 학파 고급 카드 해금 | 각 학파 10레벨 |
| 도서관 연구 | 학습 노트 | 시작 마나 +5%, 결계 체력 +10% | 12개 노드 |
| 주문 강화 | 마력 잉크 | 특정 주문 피해/범위 강화 | 주문별 3단계 |

## 8. 런칭 콘텐츠 범위

런칭 범위는 작지만 부족해 보이지 않도록 ‘반복 조합 수’를 확보하는 데 집중한다. 스테이지 숫자를 과도하게 늘리는 대신, 학파 조합과 강화 카드 풀로 리플레이성을 확보한다.

| 분류 | 수량 | 비고 |
|---|---|---|
| 챕터 | 3 | 기초시험 / 응용시험 / 승급시험 |
| 스테이지 | 30 | 챕터당 10개 |
| 보스 | 3 | 챕터 최종 보스 |
| 학파 | 4 | 화염, 냉기, 보호술, 연금학 |
| 핵심 주문 | 16 | 학파당 4개 |
| 공통 패시브 | 12 | 쿨다운, 범위, 치명, 결계 보강 등 |
| 유물 | 8 | 한 판 방향성을 바꾸는 특수 효과 |
| 적 타입 | 12 | 소형, 분열, 방패, 비행, 보스 등 |
| 일일 도전 | 1 | 매일 규칙이 바뀌는 과제 |

> **콘텐츠 전략** ‘수량을 무리하게 늘리지 않고 조합 수를 늘린다’가 원칙이다. 런칭 수치만으로도 4학파 × 16주문 × 패시브 조합으로 반복 플레이 동기가 충분하다.

## 9. 경제 구조

경제는 2통화 + 광고 보조로 제한한다. 프리미엄 재화를 넣지 않으면 밸런스와 UX가 단순해지고, 토스 첫 런칭용 실험으로도 관리가 쉽다.

| 재화 | 획득처 | 사용처 | 비고 |
|---|---|---|---|
| 학습 노트 | 기본 스테이지 클리어 | 도서관 영구 업그레이드 | 주요 소프트 재화 |
| 마력 잉크 | 보스 클리어, 일일 도전, 광고 선택 보상 | 주문 강화 | 희소 재화 |

- **광고 없는 기본 보상은 충분해야 한다: **광고는 가속 장치이지 필수 통행료가 되면 안 된다.
- **실패 보상도 60~70%는 지급한다: **재도전 의지를 남긴다.
- **초기 업그레이드는 3판 안에 체감되게 한다: **바로 강해졌다는 감정이 중요하다.

## 10. 광고 및 수익화 기획

토스는 전면형, 보상형, 배너 광고를 제공하고, 광고를 수익 수단으로 쓰되 사용자 경험을 해치지 않는 것이 가장 중요하다고 명시한다 [T4]. 이 기획서에서는 출시 스코프를 줄이기 위해 ‘보상형 + 전면형’만 MVP에 포함하고 배너는 제외한다.

| 광고 유형 | 사용 여부 | 노출 위치 | 사용 목적 | 운영 원칙 |
|---|---|---|---|---|
| 보상형 | 예 | 실패 후 이어하기 / 결과 x2보상 / 수업 리롤 | 핵심 수익화 | 사용자 선택시에만 노출, 시청 완료시에만 보상 |
| 전면형 | 예 | 결과 화면에서 다음 스테이지 진입 전 | 보조 수익화 | 판 사이 전환점에서만, 첫 접속/튜토리얼에는 미노출 |
| 배너 | 아니오(MVP) | 해당 없음 | 출시 후 검토 | 게임 화면 중앙 금지, 상·하단 빈영역 규칙 때문에 MVP 제외 |

권장 빈도는 다음과 같다. 전면형 광고는 결과 화면에서만 보여 주되, 최초 세션과 튜토리얼 단계에서는 꺼 둔다. 또한 4분 쿨다운과 세션당 1회 제한을 두어 과도 노출을 방지한다. 보상형 광고는 부활 1회, 결과 x2 보상 1회, 수업 리롤 1회 등 명확한 가치를 제시하는 위치에만 둔다. 이는 공식 문서의 ‘예상하기 어려운 순간 금지’, ‘보상 완료 이벤트에서만 지급’, ‘빈도 제한·쿨다운 필요’ 원칙을 실제 게임 룰로 번역한 것이다 [T5][T6].

> **정산 관점** 광고 연동 전에는 사업자 정보와 정산 정보를 등록하고 검토를 받아야 하며, 광고 그룹 생성 뒤 발급된 ID가 구글 등록까지 최대 2시간 걸릴 수 있다. 광고 성과는 익일 오전 4시에 업데이트되고, 세금계산서 승인 기한을 넘기면 정산이 이월될 수 있다 [T7][T8]. 따라서 QA/출시 일정에는 광고 ID 반영 대기와 정산 승인 운영을 미리 포함해야 한다.

## 11. UX / UI 상세

UI는 ‘게임 화면’과 ‘비게임 화면’을 분리해 생각한다. 게임 화면은 풀스크린 세로형으로, 결계석·적·주문 아이콘·선택 카드만 보이는 최소 인터페이스를 유지한다. 비게임 화면인 로비, 결과, 도서관, 수업 선택은 토스 디자인 시스템 톤에 맞게 단순 카드형으로 정리한다. 앱인토스는 앱빌더를 통해 토스 스타일 가이드에 맞는 화면을 빠르게 만들 수 있게 지원하므로, 비게임 화면은 앱빌더/퀵스타트 계열로 먼저 조립하는 편이 효율적이다 [T9].

| 화면 | 목적 | 구현 원칙 |
|---|---|---|
| 브릿지/인트로 | 앱 진입 | 10초 이내 첫 화면 도달, 자동 광고/바텀시트 금지 |
| 로비 | 수업 선택과 진척 확인 | 오늘의 3과목 카드, 진행도, 설정 진입 |
| 수업 선택 | 시작 빌드 결정 | 과목 3지선다, 설명 짧고 CTA 명확 |
| 전투 | 핵심 플레이 | 전체 화면, 카드 선택 외 조작 최소화 |
| 결과 | 보상 수령과 광고 포인트 | 기본 보상 우선 표시, 추가 보상은 선택형 |
| 도서관 | 영구 성장 | 단순 트리형 업그레이드, 재화 소모 결과 명확 |
| 설정 | 사운드/진동/도움말 | 사운드 On/Off 제공, 종료 경로 보장 |

게임 출시 가이드와 다크패턴 방지 정책을 반영해, 앱 진입 직후 바텀시트를 띄우지 않고, 종료를 막는 유도 팝업도 두지 않는다. CTA는 ‘광고 보고 이어하기’, ‘기본 보상 받기’, ‘다음 시험 시작’처럼 결과가 명확하게 드러나는 문구만 사용한다 [T3][T10].

## 12. 기술 구현 제안 (바이브 코딩 기준)

구현 방식은 WebView 기반을 우선 권장한다. 앱인토스는 WebView와 React Native 기반 SDK를 제공하고, 게임도 쉽게 빠르게 개발할 수 있도록 안내한다 [T1][T2]. 그러나 이번 프로젝트는 오토배틀 중심의 2D 게임이므로, 무거운 엔진보다 WebView + React + TypeScript + 간단한 Canvas 레이어가 스코프 관리에 더 유리하다.

| 영역 | 권장 선택 | 이유 |
|---|---|---|
| 앱 프레임 | WebView | 토스 문서와 Vite/React 가이드 활용이 쉬움 |
| 화면 제작 | 앱빌더 + React 컴포넌트 | 비게임 화면을 빠르게 구성 가능 |
| 게임 화면 | Canvas 2D 기반 경량 렌더링 | 오토배틀 구조라 고사양 엔진 불필요 |
| 유저 식별 | getUserKeyForGame | 서버/동의 절차 없이 식별 가능 |
| 저장 | 로컬 저장(MVP) | 서버 없는 MVP에 적합 |
| 선택형 확장 | Firebase 백업 | 공식 문서가 WebView+Vite 기준 가이드 제공 |

게임 로그인은 게임 카테고리 미니앱 전용이며, 동의 절차와 서버 연동 없이 안정적인 유저 식별자를 즉시 얻을 수 있다. 공식 문서는 이 방식이 로그인 약관 단계의 높은 이탈을 줄이는 데 유리하다고 설명한다 [T11][T12]. 따라서 MVP는 토스 로그인이나 자체 로그인 대신 게임 로그인을 전제로 잡는 것이 맞다.

또한 앱인토스는 AI 개발 가이드에서 MCP와 llms.txt/llms-full.txt 문서를 통해 AI가 SDK/API 문맥을 더 잘 이해하게 할 수 있다고 안내한다 [T13]. 즉, Cursor·Claude·Codex 기반의 바이브 코딩을 실제 공식 개발 흐름 안에서 활용할 수 있다. 초기 세팅은 ‘앱인토스 llms.txt 등록 → 앱빌더로 로비 뼈대 생성 → WebView 게임 화면 구현 → 샌드박스/QR 테스트’ 순서가 가장 효율적이다.

> **MVP 기술 원칙** 서버, 실시간 기능, 복잡한 API를 일부러 빼서 mTLS·백엔드·운영 복잡도를 만들지 않는다. 게임 로그인 + 로컬 저장 + 광고 SDK만으로 런칭 가능한 구조를 우선 확보한다.

## 13. QA 및 검수 체크리스트 반영

광고 QA 문서와 게임 출시 가이드를 제품 규칙으로 미리 옮겨 놓으면, 개발 막판에 급하게 고치지 않아도 된다.

| 체크 항목 | 제품 설계 반영안 |
|---|---|
| 최초 화면 10초 이내 | 인트로 최소화, 리소스 분할 로딩 |
| 사운드 On/Off 제공 | 설정 화면 첫 메뉴에 배치 |
| 백그라운드 전환 시 사운드 정지 | 앱 생명주기 훅으로 즉시 pause |
| 광고 사전 로드 | 로비 진입/결과 화면 진입 시 preload |
| 광고 종료 후 정상 복귀 | 결과 화면 상태 복원용 state 유지 |
| 시청 완료시에만 보상 지급 | 보상형 완료 콜백 외 경로 지급 금지 |
| 중복 보상 방지 | 광고 ticket 소모 플래그 도입 |
| 빈도 제한·쿨다운 | 전면형 4분 쿨다운, 세션 1회 제한 |
| 인트로/로딩/팝업에 광고 금지 | 광고 호출 위치를 결과/부활 화면에만 제한 |
| 종료 경로 제공 | 상단 닫기 버튼 + 종료 확인 모달 |
| 플레이 기록 유지 | 로컬 저장 주기적 flush |

## 14. 라이브 운영과 지표

MVP의 라이브 운영은 매우 작게 시작한다. 시즌제보다 ‘일일 도전 규칙 하나 바꾸기’만으로도 충분하다. 운영 목표는 콘텐츠 양보다 반복률과 광고 체감의 건강성을 보는 것이다.

| 지표 | 목표 | 해석 |
|---|---|---|
| 튜토리얼 완료율 | 70% 이상 | 첫 화면과 첫 판 진입의 마찰 확인 |
| D1 리텐션 | 25% 이상 | 짧은 세션 구조의 재방문성 확인 |
| 평균 세션 길이 | 4분 내외 | 토스 앱 맥락에 맞는지 확인 |
| 보상형 광고 선택률 | 15~25% | 광고 가치 설계 적정성 확인 |
| 전면형 광고 이탈 증가 | 유의미한 상승 없음 | 빈도 과다 여부 판단 |
| 평균 첫 화면 로드 | 6초 이하 | 10초 요구 대비 여유 확보 |
| 광고 오류율 | 2% 미만 | 사전 로드/복귀 품질 확인 |

## 15. 4주 제작 로드맵

| 주차 | 핵심 산출물 | 세부 작업 |
|---|---|---|
| 1주차 | 플레이어블 프로토타입 | 로비/수업 선택/전투 기본 루프, 결계석 방어, 1챕터 5스테이지 |
| 2주차 | 메타/저장/광고 연결 | 도서관 업그레이드, 로컬 저장, 게임 로그인, 보상형 광고 |
| 3주차 | 콘텐츠 확장/전면 광고/사운드 | 30스테이지, 4학파, 사운드/설정, 전면 광고, QA 보정 |
| 4주차 | 검수 대응/심의/출시 준비 | 실기기 테스트, 광고 테스트 ID 점검, 심의 자료, 아이콘/브랜드 정리 |

이 일정은 앱인토스가 안내하는 ‘게임은 약 2~4주면 출시 가능’이라는 범위 안에 있지만 [T1], 실제론 게임 심의와 광고/정산 준비를 생각하면 4주를 가득 쓰는 편이 안전하다. 특히 광고 그룹 생성 후 ID 반영 대기, 실기기 QA, 사운드/복귀 예외 처리를 반드시 마지막 주 전까지 끝내야 한다 [T6][T7].

## 16. 최종 제안

토스 미니앱에서 가장 중요한 것은 ‘작고 선명한 성공 경험’을 만드는 것이다. 그래서 이 프로젝트는 기존의 마법학교 판타지를 모두 담으려 하지 않고, 그중 가장 강한 문장 하나만 남긴다. 바로 ‘원하는 마법 수업을 골라 듣고, 그 결과를 오늘의 시험에서 확인한다’는 구조다.

이를 위해 출시 버전은 세로형 오토배틀, 2~3분 세션, 게임 로그인, 광고 우선 수익화, 배너 제외, 서버 없는 MVP, 4학파 30스테이지로 제한한다. 이 구성이면 토스의 UX와 광고 정책을 어기지 않으면서도, 바이브 코딩으로 충분히 구현 가능한 수준에서 차별화된 게임을 만들 수 있다.

> **한 줄 결론** 토스판 ‘마법학교 게임’의 정답은 대작 RPG가 아니라, 수업 선택과 실기시험을 3분 안에 끝내는 가벼운 오토배틀 미니앱이다.
